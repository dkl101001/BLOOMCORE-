# BLOOMCORE FAQ Source Matrix

**Purpose:** Trace each major FAQ answer to the canonical or evidentiary artifact that supports it.  
**Rule:** This matrix records authority; it does not create authority. An unsupported row remains unsupported until an appropriate source or implementation receipt is reviewed.  
**Review date:** 2026-07-30

## Status vocabulary

| Status | Meaning |
|---|---|
| **Canonical** | The source declares an active canonical or locked status within its stated scope. |
| **Master** | The source is the current master treatment found for a bounded subsystem. |
| **Proposed** | The source proposes a canonical patch or future integration but is not treated as fully ratified. |
| **Executable evidence** | Code, tests, manifests, hashes, or receipts support an implementation claim. |
| **Historical** | Useful for lineage; not authoritative where a current canonical source supersedes it. |
| **Relational / project history** | Identity-bearing history preserved as history, not scientific proof. |
| **Incomplete** | Relevant evidence exists, but the reviewed source set does not support the full public claim. |
| **Unsupported** | No reviewed canonical source or sufficient evidence was found. |

## Source precedence

When sources disagree, the FAQ uses this order and reports unresolved conflicts:

1. explicit boundary requirements for this documentation build;
2. active Phase 36/37 merged canon;
3. explicit canonical subsystem locks;
4. current master specifications and whitepapers;
5. proposed or provisional reconciliation documents;
6. executable code, tests, receipts, manifests, and hashes;
7. historical lineage sources;
8. relational or project-history material.

Executable evidence can prove that an implementation ran or passed a stated test. It cannot silently rewrite canonical meaning. Conversely, canonical prose cannot prove that software exists or that an empirical result occurred.
